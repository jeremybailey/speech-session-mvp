## Deployment isolation finding

The first post-fix synthetic overview completed under validator v2, despite the public alias targeting the v3 deployment. It therefore did not test the newly deployed validator/prompt. Vercel Queues pin messages to the deployment that created them. The self-scheduling heartbeat let an old deployment repeatedly scan shared work and create old-version jobs after promotion. Earlier synthetic readiness checks did not bind the executing worker version to the promoted deployment; their new-key validation claim was too strong.

Migration 011 adds an operational active-deployment row. New incremental API submissions, scheduling, saved-result replay, heartbeat renewal, job submission, and publication check that row. A superseded worker stops; activation is an explicit release step after readiness. Synthetic database coverage verifies that an old deployment neither submits nor recovers work and the new deployment resumes the same durable unit. Old deployments predating this guard must be retired once, after the replacement is ready, because their immutable code cannot honor the guard. Deployment retirement does not delete application database records. Official behavior: https://vercel.com/docs/queues/concepts#deployments-and-versioning .
